02

Launch

Stage 2 of 4

Five thousand ads at once, and none of them spending

Generated pages earn nothing until campaigns point at them, and campaigns were being built in Ads Manager by hand.

Meta Ads bulk uploader

Built and deployed solo · 2026

A partner hands over a spreadsheet. The tool turns it into Meta Ads Manager campaigns, up to 5,000 ads per file.

  • Every entity is created paused. Nothing spends until an operator deliberately turns it on, which is what makes a 5,000-row run safe to attempt.
  • One Python package drives two front ends over one SQLite database, so a run started on the command line can be finished in the browser. A CLI for engineers, a web UI for the business team.
  • Server-rendered HTML with htmx, and Server-Sent Events so a long push reports progress instead of hanging.
  • A real pytest suite across parsing, the push orchestrator, ad sets, the rate limiter and end-to-end, plus a deploy kit behind systemd and nginx.
Read the deep dive Python 3.11 · FastAPI · htmx · SSE · SQLite

03

Gate

Stage 3 of 4

Checking a campaign before Google ever sees its traffic

A policy strike from an ad network arrives as an account problem, after the traffic has already run. So the check has to happen before the click.

RAF compliance proxy

Publabs · 2025–2026

A transparent proxy that sits in the click path and validates a campaign against network policy before its traffic reaches Google's search units. It was the largest thing I owned in that era.

  • An LLM auto-approval layer that rules on campaign compliance, so the review queue only sees what the model won't clear on its own.
  • HMAC-signed requests, so the proxy can prove a validation call came from a source it trusts.
  • A Redis-backed approval state enforced in real time, and a review API where a human approves or rejects with a comment.
  • A polling service that detects creative changes after approval and pauses the campaign, because an approved ad that quietly swaps its image is no longer an approved ad.
  • Redis re-architected for scale: key prefixing, SMEMBERS instead of KEYS, and account-level separation so tenants can't read each other's state.
  • Integrated per network, starting with Meta in production, then Google Ads, TikTok Ads, Bing, Outbrain and Taboola.

04

Serve

Stage 4 of 4

So I started building the serve layer

If the answer surface is where attention is going, then the ad units belong inside the answer. I built the proof of concept for that from scratch, and it became a second product. I started the build and I'm a founding engineer on it.

Embeddable AI answer surface

Second product · in development

A publisher drops in one <script> tag and gets an answer surface on their own site, monetised with ad units placed inside the answer.

  • Retrieval-augmented against a per-partner content manifest, with embeddings-based relevance scoring, so answers are grounded in that publisher's own pages.
  • Closed Shadow DOM, so the publisher's CSS and the widget's CSS cannot reach each other. On someone else's site that isn't a nice-to-have.
  • Origin-allowlist auth on partner key plus browser origin. A leaked key used from a domain that isn't on the list gets a 403. An admin can rotate a key and invalidate open sessions, or switch a partner off.
  • Eight ad placements across search, display and affiliate stacks, each one toggleable per partner from a config API.
  • An admin console for partner registration and embed-snippet generation, with theme inheritance that reads the host page's fonts and colours.
  • A deliberately hostile demo site, built to fail the origin check, so the 403 is something you can watch happen.

01 / identity

IAM v3, clean slate

The previous identity model couldn't express the customer shape we needed, so I rebuilt it rather than patched it.

  • three-tier org hierarchy
  • dynamic roles + permission mapping
  • SSO, JWT, invite flows
  • org-based access control
Deep dive
02 / latency

Roughly 8× on the degraded path

A dead Redis was costing about two seconds per operation, and five of those in a row timed a page out. The fix was to stop waiting.

  • circuit breaker: fail fast, alert on open
  • cluster client + L1 cache
  • N+1 elimination
  • 2s → 0.25s per operation
03 / storage

S3 to Google Cloud Storage

Moved image and asset storage across clouds on both the backend and the frontend, with a CDN cutover and a backfill of everything already in flight.

  • bucket flip + DNS cutover
  • backfill from the old provider
  • done under the launch track
04 / hardening

Security hardening for launch

I owned the security work ahead of the launch review: how long a session stays usable, who can reach an administrative route, and what a sign-out actually clears.

  • layered session invalidation
  • idle timeout and a hard cap
  • authorisation gates on admin routes
  • sign-out that clears client state
Tier 1Organisation. Holds the top-level grant of modules.
Tier 2Business. A product boundary inside the org. Routes are gated on whether one is active.
Tier 3User. Holds dynamic roles, resolved to permissions per request.

The hierarchy took the longest to get right. Everything above now resolves against it.
