The embeddable answer surface

One script tag puts an answer surface on someone else's website, with the ad units inside the answer rather than around it.

What it isA second product, now in development. No public repo.
When2026 – ongoing
StackVanilla JS, closed Shadow DOM, FastAPI, embeddings
My roleFounding engineer. I started the build and wrote the proof of concept end to end: SDK, backend and admin console.

Why build it

The pipeline I work on ends at a boundary. Compliant traffic reaches a search-ad surface that somebody else operates, and that surface takes the interesting part of the decision: what answer the reader sees, and what commercial units sit next to it.

Search traffic is shifting from link lists to answers. A publisher who runs the answer surface on their own site keeps the monetisation attached to it. I built a proof of concept to find out what standing one up requires. The model call was the smallest part, and the proof of concept was convincing enough that it became a product we're now building.

The three problems that matter

A widget on your own site is easy. A widget on a stranger's site has to survive their CSS and prove it is allowed to be there. It also has to answer from their content, without inventing things about their business.

Isolation

The widget lives in a closed Shadow DOM. Partner CSS can't reach in and restyle it, and its own styles can't leak out and break their page. Closed rather than open matters here: with an open root, any script on the host page can walk into the widget's internals, and one of those scripts is often an analytics tag nobody audited.

It mounts inline, filling a page the publisher designates, rather than floating as a bubble in the corner. Something meant to carry the publisher's own content should sit in their layout.

Auth that survives a leaked key

A partner key shipped in client-side JavaScript is public. Anyone can read it out of the page, so treating it as a secret would be theatre. Requests are authorised on the pair of key and browser Origin, checked against a per-partner allowlist. A key lifted from a partner's page and replayed from another domain gets a 403.

An admin can rotate a key, which invalidates open sessions, or disable a partner outright. I also built a deliberately hostile demo site whose only job is to fail the origin check, so the 403 is something you can watch happen.

Grounding

Answers are retrieved against a per-partner content manifest with embeddings-based relevance scoring, so the surface answers from that publisher's own pages. A general-purpose model answering questions under a publisher's brand is a liability for them. Retrieval keeps the answer inside content they already stand behind, and it keeps the ad units contextually connected to the thing being asked about.

Decisions, and what each one cost

Closed Shadow DOM

Nothing on the host page can reach the widget's internals.

cost Debugging on a partner's site gets much harder, because you can't inspect from the console the way you normally would. It also blocks legitimate host-page integrations, which is why theme inheritance had to be built explicitly instead of inherited for free.

Reading the host page's theme instead of asking for it

The console reads the partner's fonts and colours via getComputedStyle and pulls a colour from their favicon, so the surface looks like it belongs without an onboarding form.

cost It is inference, so it is sometimes wrong. The admin console has a primary-colour override for exactly that.

Ad placements defined as config, not code

Eight placements across search, display and affiliate stacks, each independently toggleable per partner through a config modal and a PATCH endpoint.

cost Eight placements is more surface than any single partner will want, so the default matters a lot and a bad default makes the product look greedy.

A mock backend, to prove the model before building the real one

The FastAPI backend behind it mocks the parts that would be real infrastructure, so the embed, auth and monetisation flows could be exercised end to end quickly.

cost It proves the integration model. The serving economics are untested, and this is a prototype rather than something carrying traffic.

What the proof of concept already does

  • A single embeddable JavaScript file that a partner adds with one script tag.
  • An admin console for partner registration, embed-snippet generation, a test-live view, primary-colour theming, and a recent-activity feed.
  • Multi-vertical content awareness, so the surface adapts to what kind of publisher it's on.
  • Demo partner sites, including the spoof site that gets rejected.
What I'd change

There are no evals yet. For a proof of concept whose point was the embed and auth model that was the right thing to skip. Now that it's a product, it's first on my list: a retrieval-quality harness with a fixed set of questions per partner manifest, scored on whether the answer is actually supported by a retrieved page. Without that you cannot tell an improvement from a regression.
