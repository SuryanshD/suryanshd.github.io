The Meta Ads bulk uploader

A partner sends a spreadsheet. It becomes up to 5,000 ads in Meta Ads Manager, and not one of them can spend money until somebody deliberately turns it on.

WhereInternal tool at InMobi. Private repo.
When2026
StackPython 3.11, FastAPI, Jinja2, htmx, SSE, SQLite (WAL), systemd, nginx
My roleBuilt, tested and deployed it solo, end to end

The problem

Campaign structures were being built by hand in Ads Manager. That works for ten ads. At a few thousand it is not something a person does, and hand-entry is where the expensive mistakes come from, because a wrong budget on a live ad spends money immediately.

The partner already had the information in a spreadsheet. Everything needed was in there. What was missing was something that could turn it into a campaign structure without a human transcribing it row by row.

The one decision that made it trustworthy

Every entity is created paused. Campaigns, ad sets and ads, all of it.

With everything paused, the worst a bug can do is leave objects to delete. The go-live decision moves to a person who is looking at what was actually created.

Decisions, and what each one cost

One package driving both front ends over a shared database

Engineers want a command line: parse, then videos, then push. The business team wants a page with a button. Both drive the same code against the same SQLite file, so a run has one state rather than two.

cost The shared state has to be safe for two writers, which is why SQLite runs in WAL mode. Simpler than the alternative, which is two tools that disagree about what happened.

htmx and server-rendered HTML instead of a frontend framework

The UI is forms, a table and a progress view. Jinja templates with htmx cover all of it and the whole tool stays one deployable Python process.

cost Rich client-side interaction would be awkward. It doesn't need any. This is the sort of tool that gets abandoned if it has a build pipeline to maintain.

Server-Sent Events for progress

Pushing thousands of entities takes a long time. SSE streams progress so the page reports what's happening instead of appearing hung.

cost A long-lived connection through nginx needs its buffering and timeouts configured correctly, which is a deployment detail that will bite whoever forgets it.

A single-worker FIFO queue rather than parallel pushing

Concurrency would be faster right up until the API rate limit, at which point failures arrive interleaved and partial state gets very hard to reason about. One worker, in order, behind a rate limiter.

cost A 5,000-ad run takes as long as it takes. In exchange a failure is legible, because the runs happened in a known order.

Dialect-neutral schema

SQLite is right for a single-operator internal tool, but the schema avoids SQLite-specific constructs so it can move to Postgres or AlloyDB if the tool outgrows one machine.

cost Passing up some SQLite conveniences for a migration that may never happen. Cheap insurance.

The parts that make it a tool rather than a script

  • A pytest suite covering parsing, the database layer, templates, reporting, the rate limiter, the push orchestrator, ad sets, videos, and an end-to-end path.
  • A deploy kit: a systemd unit, reverse-proxy config, and deploy, backup and cleanup scripts.
  • Signed-cookie session auth, so the web UI isn't open to whoever finds the host.
  • Optional email over AWS SES for run outcomes.

The tests are the reason I trust it. Most of the failure surface is in parsing partner spreadsheets, and no two of those arrive shaped the same way.

What I'd change

I delivered it as a single drop rather than in reviewable pieces. Nobody could read it incrementally, and the history does not explain why any particular decision was made. The tool is fine; the way I handed it over made it harder for anyone else to pick up.

The thing I'd actually add is a dry-run diff: show the operator exactly what would be created, as a reviewable summary, before anything touches the API.
