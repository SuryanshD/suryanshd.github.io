What it has to produce

A page that earns has to satisfy two audiences that want different things. A reader wants something worth reading. The ad network wants a page whose content genuinely matches the keywords the ad units are querying against, and it will demote or refuse pages where that relationship is thin.

So the output isn't an article. It's an article, a headline set, images at the right aspect ratio, and the ad-unit specification for that page, all of which have to agree with each other about what the page is about.

Two providers, deliberately

Gemini and Claude are both wired in, behind the same prompt engine. In practice they are not interchangeable: each one wants the templates' structured output shaped a little differently. Having two also means a provider incident degrades the product instead of stopping it.

The prompt engine

Each content feed needs the generation to behave differently, so prompts are configuration rather than strings next to the call site: composed per feed, overridable per article. Changing how one feed generates does not mean touching the others.

Semantic image search

Generating a fresh image every time is slow and expensive, and the platform accumulates a large asset library anyway. The Image Hub indexes assets as embeddings, so an editor finds an image by describing it rather than by remembering a filename. I built the universal-access module for it, ran the database migration and the backfill, added vertical and content-type metadata to AI-generated images, and got the search endpoint working reliably.

Decisions, and what each one cost

Prompts as configuration rather than code

Per-feed and per-article prompt config, changeable without a deploy.

cost Prompt behaviour is now spread across configuration rows, so reproducing a bad output means knowing exactly which config produced it. That's an argument for versioning prompt config, which I'd add next.

Migrating imagery to Imagen 4

Imagery moved to Imagen 4, and a 16:9 WebP pipeline standardised the output for the templates that hold the ad units.

cost A migration mid-product, with the older assets still in circulation, so the library holds two generations of imagery and the newer tags don't exist on the old ones.

Streaming discovery instead of a request that finishes

Concept rediscovery takes long enough that a plain request-response would time out, so it streams progress.

cost This is the part that broke in production. Streaming makes the client feel fast and moves the failure modes into infrastructure, which is where I then had to go fix them.

Stabilising it under real load

Discovery worked, then didn't, once it was running against real volumes. Fixing it was unglamorous and worth recording precisely:

  • The distributed lock TTL is held ahead of the run timeout, so a long run cannot have its own lock expire underneath it.
  • Container memory limits and filesystem permissions were sized to the workload rather than left at defaults.
  • Exception tracebacks became structured JSON, because an unparseable stack trace in a log aggregator is nearly useless.
  • On the frontend, a proxy was doubling the query string, which broke one feed specifically. That one took longer to find than it should have.

Almost none of it was model work.

What I'd change

I'd build the output checks before the generation. The specific thing I'd add is an automated check that the article and the ad-unit keywords agree.
