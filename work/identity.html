Foundation · Identity / Deep dive

Identity, rebuilt from scratch

The old model couldn't express the customer shape we were selling into, so we replaced it rather than kept bending it.

WhereA new AI monetization platform at InMobi
WhenMar – Jul 2026
StackPython, FastAPI, AlloyDB, Redis, Next.js, SSO, JWT
My roleOwned it end to end, backend and frontend. One of three engineers on the platform.

Why replace rather than patch

The product needed an access model with more structure than the one it started with, and the gap was being covered by convention rather than by the model itself.

That kind of gap shows up as a slow accumulation of places where "is this person allowed to see this" gets answered slightly differently. So IAM v3 was a clean slate.

The three tiers

The whole design is one decision: identity has three levels, and every authorisation question resolves against them in order.

Dynamic roles

Roles are rows with permission mappings, so a customer can be given a shape nobody anticipated at build time without a code change. That was the point.

The active-business gate

Product routes sit behind a require_active_business dependency. It reads simple and it removes a whole class of bug, because a route can no longer accidentally serve data without having established which business boundary it's operating inside.

Invites, SSO, and the parts that actually go wrong

Sign-in is hosted by the identity provider and self-signup is removed, so the application never sees a password. Most of the real work was in the seams:

  • Environment-correct redirects. The sign-in URL is built server-side from runtime environment rather than baked in, so each environment resolves to its own auth domain.
  • Relative callbacks. Absolute redirect URLs resolved to localhost once the app was behind a public host, so callbacks became relative.
  • A plain anchor for the sign-in call to action. A client-side route transition triggered a cross-origin fetch to the identity provider and failed CORS. It needed to be a full navigation, which is a good reminder that auth flows and client routers want different things.
  • Reconciling users by email on login. A user's identifier at the provider can change across tenants, and treating that as a new person orphaned their access. Login now reconciles on email.
  • Invite auto-heal. Invites could land in a state where the row existed but the user couldn't complete it, so the flow repairs itself rather than needing an operator.

Decisions, and what each one cost

Three tiers, not two, and not arbitrary nesting

One level of grouping could not express an organisation holding separate businesses. Arbitrary depth would have made every permission check a recursive walk and every UI a tree.

cost Anyone who genuinely needs a fourth level has to model it awkwardly. I would rather widen it if that arrives than carry the recursion now.

Typed 409s instead of generic failures

Conflicts during invite and provisioning return a typed conflict, so the frontend can tell the user which specific thing collided.

cost More error surface to define and keep in sync between backend and UI. Cheaper than support conversations about an opaque failure.

Caching resolved permissions, with explicit invalidation

Resolving roles into permissions on every request is the obvious way and it is work repeated constantly, so the result is cached with Cache-Control and cleared when a grant or role changes.

cost Every write path that touches roles now has to remember to invalidate. This is the part of the system I'd most want a second pair of eyes on.

Session lifetime

Ahead of the launch review I went through session lifetime and administrative access properly. Invalidation ended up layered, because no single mechanism covers all of it:

  1. A provisioning gate, so a user who isn't fully set up can't hold a working session.
  2. An epoch, so bumping a value invalidates every existing session for a user at once.
  3. An idle timeout for the abandoned-laptop case.
  4. A hard 24-hour cap, so no session outlives a day regardless of activity.

Sign-out became provider-initiated, clearing cookies and sending Clear-Site-Data, with no-store on authenticated routes so the back button can't paint a logged-in page after sign-out. Administrative authorisation moved server-side behind explicit gates. I also cleared the dependency audit and stopped the container from shipping dev dependencies.

What I'd change

The hierarchy took the longest to settle and I changed my mind about it twice while code was already depending on it. If I did it again I'd write the permission-resolution rules down as a table and get them agreed before building the data model, because the model follows from the rules and I did it in the other order.
